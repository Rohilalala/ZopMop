# Zopmop Codebase + Business Audit — 2026-05-03

## Summary

The backend Go service compiles cleanly and the security posture is solid (auth gating, parameterized SQL, Firebase verification, capped PostGIS radius). The user RN app fails `tsc --noEmit` with 29 errors caused by a missing `svg.d.ts` shim — a one-line shim unblocks it. The largest red flags are commercial, not structural: the entire payment path is a UI stub (no order-creation endpoint, no webhook handler, bookings are persisted before any charge succeeds), the rating endpoint silently 404s, and pro payouts are 100% manual with no earnings surface for the pro. Several "coming soon" gates (privacy policy, ToS, notification settings, wallet) remain in user-facing screens. CRM-v2 scaffolds (orders/refunds/promos/banners/A-B/analytics/growth/payouts/T&S/platform) are large new surfaces with zero test coverage. Net: not launchable to real users today; ~6–10 P0/P1 fixes stand between current state and a usable beta.

### 4. Security

#### 4a. Handlers without auth middleware

Public (intentional): `/health`, `/ready`, `/auth/send-otp`, `/auth/verify-otp`, `/auth/firebase`, `/auth/logout`, `/api/v1/app/*`, `/api/v1/services/*`, `/api/v1/zones/*`, `/api/v1/localities/*`, `/api/v1/insights/nearby` (coarse aggregate, no PII), `/api/v1/sdui/page/:page_id` (optional auth via `c.Locals`). CRM equivalents: `/health`, `/ready`, `/admin/auth/send-otp`, `/admin/auth/totp/verify`, `/admin/auth/refresh`, `/admin/auth/logout`.

All authenticated route groups (`/bookings`, `/location`, `/addresses`, `/cart`, `/slots`, `/places`, `/payments`, `/me`, `/helpers/*` w/ `RequireRole("pro")`, `/pro/leave/*`, `/admin/*`) pass through `authMiddleware` + appropriate limiter. **No accidentally-unprotected routes.**

#### 4b. IDs from request body

User identity is consistently sourced from `c.Locals("userID")` (JWT). Body fields named `customer_id`, `helper_id`, `user_id` exist only on response DTOs; they are **never decoded as request overrides**. Verified in `addresses`, `cart`, `booking`, `location` handlers.

#### 4c. SQL injection via concatenation

All Postgres queries use parameterized `$1/$2…` placeholders. Reviewed `matching/engine.go` (lines 248, 394, 404, 523), `location/handler.go:206`, dispatch/scheduled/stealth dispatch. `fmt.Sprintf` is only used for **Redis keys** (no SQL parser involved). **No SQL injection found.**

#### 4d. Firebase ID token verification

`internal/auth/firebase.go:51` calls `client.VerifyIDToken(ctx, idToken)`. `POST /auth/firebase` (handler.go:64) is the only Firebase ingress and it always verifies before issuing app JWT. **No bypass.**

#### 4e. PostGIS radius cap

Radius is **never user-controlled**. `matching/engine.go:590` defines `MaxRadiusKm: 15.0` (hardcoded default). Initial search uses `cfg.RadiusKm` (5km), expansion capped at `cfg.MaxRadiusKm`. Redis GEOSEARCH and Postgres fallback both consume the engine config, not request input. `insights/handler.go:34` accepts only `lat/lon`, no radius parameter. **The 50km figure in the brief overstates the cap; actual ceiling is 15km.**

## Part 2: Business

### 8. Business Model vs Implementation

**Customer charge today:**
- Flat platform base fee `₹20` (2000 cents). `internal/config_manager/model.go:45` `ConfigPricingBaseFeeCents = "2000"`.
- Total formula (`internal/booking/service.go:162`): `totalPriceCents = basePriceCents + pricingConfig.BaseFeeCents`.
- Optional surge multiplier (`service.go:164`): `totalPriceCents = int(float64(totalPriceCents) * pricingConfig.SurgeMultiplier)`.
- No GST, gateway fee, or insurance fee added.
- Promo discounts: percent or fixed, capped at total (`service.go:172-186`).
- Cancellation fee: ₹100 hardcoded (`internal/booking/cancellation.go` `DefaultCancellationFeeCents = 10000`), gated by `IsFreeCancellation()`/`CancellationStartTime()` whose semantics are not fully spelled out.

**Pro payout today:**
- 100% manual. `internal/crm/payouts/payouts.go:1-4` explicitly: *"Mark-paid is admin-driven; the actual bank/UPI transfer is out of scope (no provider wired)."*
- Admin creates payout (`POST /payouts`), marks paid (`POST /payouts/:id/paid`) with optional `external_ref`.
- No Razorpay/Cashfree payout API call. `/payments/validate-vpa` (`payments/handler.go:81-117`) only validates UPI accounts.
- **No commission split logic visible.** No code computes `pro_earning = customer_charge − platform_take`. Pro never sees a number.

**Other revenue mechanics:** None. No subscription, no tiered commission, no surge above the multiplier knob, no convenience fee.

**Verdict:** Customer side computes a price; pro side is opaque manual. Unit economics cannot be reconstructed from the codebase alone — there is no formal split written down in code.
